# Task 3.0：执行链路与实时可观测

[返回 Phase 3](README.md)

## 目标

复用 Phase 1.5 的 telemetry，让提交后的真实执行阶段、已用时间、重试和最终结果持续可见。保留 POST JSON 与 Answer 原子提交；进度流是业务执行的只读投影。

## 执行边界

- Server 分离路由、执行编排、SQLite 存储与遥测；前端分离会话提交/恢复和进度订阅。
- 每次领取命令使用独立 owner；整轮 deadline 覆盖所有请求与重试，短于租约并预留提交时间；过期旧执行不能提交或释放新执行。
- Collector 管理 Trace/Span 生命周期，使用单调时钟计时；业务提交成功才是 Trace 成功。局部拒绝后纠正成功不使整个 Trace 失败。
- 遥测持久化与推送故障不能改写已提交的业务结果；失去进度连接不能取消业务。

## 数据与统计

Trace 区分 start、answer、narrative；Span 区分 agent、model、tool、state。记录关联 ID、运行/终态、开始结束时间、耗时、attempt、模型请求与工具纠错数量。Model Span 记录 usage、context 大小与 hash；不保存完整 prompt、工具参数或隐藏推理。

统一纯函数生成本轮、Session 和评测统计：父子耗时不叠加；token 只累计 Model Span；部分缺失显示 partial、全部缺失显示 unavailable；正常多次请求、Provider 重试、工具拒绝分别统计。p50/p95 附样本数；幂等重放不增加轮次，真实重执行保留独立 Trace。失败评测同样保存遥测。

## 传输与展示

- 保留原 POST；新增 Session SSE 只读进度，按 commandId/traceId 匹配当前执行。
- 现有 telemetry_traces 保存运行快照与最终状态。订阅发送快照，重连重新同步；刷新恢复不得重复执行命令。
- 候选人只收到允许的阶段、状态、耗时与可重试提示；技术视图读取结构化 Trace/Span。
- 提交后先显示“正在提交”，服务端确认后显示“已接收”；阶段为整理回答、准备下一问、保存结果。持续显示已用时间，不伪造百分比或剩余时间。
- 成功、失败、超时、中断均有明确终态；SSE 不可用时通过只读查询恢复。

## 验收

- 本地提交反馈目标 ≤100ms；不设服务端首次进度反馈的秒级门槛。该目标不作为服务端验收条件。
- 模拟 20–30 秒模型等待时，真实阶段和计时持续可见。
- 重试、超时、刷新、断线重连、进程重启后均能收尾；旧 owner 无法提交或释放新执行。
- 候选人进度无未校验问题、内部评估标签或原始工具结果；技术视图与 API、评测统计一致。
- grounding、完成护栏、幂等、恢复、类型检查和构建全部通过。
